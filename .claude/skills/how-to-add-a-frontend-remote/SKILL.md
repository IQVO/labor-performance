# How to add a frontend remote

Use when adding a new screen/feature to this repo's `web/` Module
Federation remote (`labor-mfe`), which already exists and is the
concrete worked example below — the shell-side half of this contract (how the console
mounts remotes) lives in the `warehouse-console` repo.

## `vite.config.ts` must stay in OBJECT form, always

This repo's `web/vite.config.ts` already gets this right — read it
before changing it:

```ts
const IS_BUILD = process.argv.includes("build");
const PUBLIC_BASE = IS_BUILD ? "/mfes/labor-performance/" : "/";

export default defineConfig({
  base: PUBLIC_BASE,
  plugins: [
    react(),
    federation({
      name: "labor_mfe",
      filename: "remoteEntry.js",
      exposes: { "./App": "./src/App.tsx" },
      shared: {
        react: { singleton: true, requiredVersion: "^19.2.8" },
        "react-dom": { singleton: true, requiredVersion: "^19.2.8" },
        "react-router-dom": { singleton: true, requiredVersion: "^7.18.3" },
        "@warehouse/ui-kit": { singleton: true },
      },
    }),
  ],
  // ...
});
```

Never convert this to the callback form
(`defineConfig(({ command }) => ({...}))`) to compute `base`
dynamically. `web/vitest.config.ts` does `mergeConfig(viteConfig,
defineConfig({...}))`, and Vite throws `Error: Cannot merge config in
form of callback` on a function export — killing the ENTIRE test suite
for a one-line config change, not just the new test. The file's own
comment documents exactly this reasoning; keep it when editing.

## A tiny, relative `dist/remoteEntry.js` after build is CORRECT

After `npm run build` with the `/mfes/labor-performance/` base,
`dist/remoteEntry.js` is a small file importing a RELATIVE path
(`./assets/virtual_mf-REMOTE_ENTRY_ID...js`) — grepping it for
`/mfes/labor-performance/` returns zero matches. That is expected, not a
bug: `dist/index.html` carries the absolute prefixed URLs, every JS
chunk uses relative ESM imports, and the module-preload helper resolves
origin-relative to wherever `remoteEntry.js` was actually fetched from —
exactly what a path-mounted remote needs. Verify correctness by serving
the built image and fetching through the real gateway path
(`http://localhost/mfes/labor-performance/`), never by grepping the
built file for the expected prefix.

## `@warehouse/ui-kit` is a sibling checkout, not a registry package

`web/package.json` depends on it via `"@warehouse/ui-kit":
"file:../../warehouse-ui-kit"`. Any domain-status color, chart, or
shared layout primitive belongs in that repo, not hand-rolled here — a
remote reinventing its own palette instead of consuming
`StatusPill`/`tokens.css` is a bug, not a style choice (visual
consistency across the MFE boundary is the #1 place MFE UX fails).

## `labor-mfe`'s `test` script already runs — confirm it still does before adding a test file

`web/package.json` already maps `"test": "vitest run"` correctly — this
remote is NOT one of the fleet's historical "no test runner at all"
gaps (which hit `inventory-storage`, `wes-work-planning`,
`fulfillment-execution`, `workforce-management`). Before assuming a new
`.test.ts`/`.test.tsx` file runs in CI, still confirm this repo's `web:`
CI job (`.github/workflows/ci.yml`) actually invokes `npm test`, not
just `npm run build` — a future package.json edit could silently regress
this. `web/src/config.test.ts`, `web/src/api.test.ts`, and
`web/src/screens/LaborPerformanceScreen.test.tsx` are this repo's
existing real examples to follow for shape (MSW-mocked API calls,
`jsdom` environment via `web/src/test/setup.ts`).

## The Docker build recipe (packaging as a deployable nginx workload)

Three traps, in order of how much time they cost when hit blind — see
this repo's own `web/Dockerfile` for the complete, working, heavily
commented recipe rather than re-deriving them from scratch:

1. **Base image must be `node:22-bookworm-slim`, not an alpine or newer
   node image.** `web/package-lock.json` was generated by npm 10 and
   carries no Linux entries for Vite's platform-specific optional
   dependencies (`@rolldown/binding-linux-*`, `lightningcss-linux-*`).
   npm 11 rejects that lockfile outright with `EUSAGE "lock file out of
   sync"`; glibc (not musl) is what matches the published `*-gnu`
   bindings.
2. **Do NOT install from the committed lockfile, and do NOT reuse a host
   `node_modules`.** Both leave the native binding missing (`Cannot find
   native binding ... @rolldown/binding-linux-*`). The working recipe:
   `rm -rf node_modules package-lock.json` in the ui-kit build stage (it
   arrives as a named BuildKit context from a developer checkout),
   `COPY package.json ./` only, then `npm install --no-save`.
3. **`@warehouse/ui-kit` must be supplied as a named BuildKit context**,
   since it's a sibling checkout, not a registry dependency. Build from
   `web/` itself (per the Dockerfile's own header comment):
   ```bash
   cd web
   docker build --build-context uikit=../../warehouse-ui-kit \
     -t warehouse/labor-performance-frontend:local .
   ```

## Wiring into `warehouse-infra`'s deploy

A new remote isn't deployed automatically — `warehouse-infra`'s
`local.services` map and this repo's own Helm chart
(`charts/labor-performance/`'s `frontend.enabled` value, default
`false`) both need updating. See `warehouse-infra`'s AGENTS.md for the
Terraform side of this; this repo only needs to ship a working chart
with `frontend.enabled` wired to a toggle.

## Key commands

```bash
cd web
npm ci
npm run lint        # oxlint (.oxlintrc.json)
npx tsc -b           # typecheck
npm test             # vitest run — confirm this actually runs your new test
npm run build         # tsc -b && vite build -> dist/
```

`labor-mfe` runs on port 5187 in local dev (`vite --port 5187` /
`vite preview --port 5187`) — this is not an arbitrary choice: this
service's own `internal/adapters/inbound/http/server.go`
`allowedOrigins()` already reserves `http://localhost:5187` in its
`CORS_ALLOWED_ORIGINS` default, predating this remote's own existence.
Keep the two in sync if either the remote's dev port or the backend's
CORS default ever changes. CI's `web:` job runs the sequence above
against a dual checkout (this repo + `IQVO/warehouse-ui-kit@develop`)
— reproduce that locally by symlinking or checking out
`warehouse-ui-kit` as a real sibling if `npm ci` behaves differently
than CI.
